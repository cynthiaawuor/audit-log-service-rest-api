# Audit Log Service REST API

An Express + TypeScript service for recording and reading audit events.

The service stores append-only audit records in PostgreSQL through Drizzle ORM. It is intended for product or platform services that need to answer questions like "who changed this resource?", "what actions did this actor take?", and "what happened during this time window?" without allowing existing audit records to be edited or deleted through the API.

## API Reference

The OpenAPI document is available at [openapi.json](/home/kali/reduzer/sprint/audit-log-service-rest-api/openapi.json:1). Load it in Swagger UI, Redoc, Stoplight, or another OpenAPI viewer to inspect every path, request body, query parameter, response, and status code.

## Tech Stack

- Node.js, TypeScript, Express 5
- PostgreSQL
- Drizzle ORM and Drizzle Kit
- Zod validation
- Docker Compose for local PostgreSQL

## Configuration

```bash
git clone git@github.com:cynthiaawuor/audit-log-service-rest-api.git
cd audit-log-service-rest-api.git

```

The server reads configuration from environment variables.

```bash
DATABASE_URL=postgres://postgres:postgres@localhost:5434/my_db
PORT=3000
```

`PORT` is optional and defaults to `3000`.

The included `compose.yml` starts PostgreSQL on host port `5434` with:

- user: `postgres`
- password: `postgres`
- database: `my_db`

## Install and Run

Install dependencies:

```bash
npm install
```

Start the local database:

```bash
docker compose up -d
```

Apply the database schema:

```bash
npx drizzle-kit migrate
```

For local development, you can also push the current Drizzle schema directly:

```bash
npx drizzle-kit push
```

Start the API:

```bash
npx tsx src/server.ts
```

The service listens on `http://localhost:3000` unless `PORT` is set.

## Event Shape

Create requests are validated with Zod. The request body for a single event is:

```json
{
  "actor_id": "user_123",
  "action": "invoice.created",
  "resource_type": "invoice",
  "resource_id": "inv_001",
  "before_state": "{\"status\":\"draft\"}",
  "after_state": "{\"status\":\"sent\"}",
  "ip_address": "127.0.0.1",
  "user_agent": "Mozilla/5.0"
}
```

Required fields:

- `actor_id`: non-empty string
- `action`: string
- `resource_type`: string
- `resource_id`: non-empty string

Optional fields:

- `before_state`: string
- `after_state`: string
- `ip_address`: IPv4 string
- `user_agent`: string

Stored events also include:

- `id`: integer primary key generated by PostgreSQL
- `timestamp`: server-side timestamp generated when the row is inserted

Note: the single-event create path currently persists the core fields only: `actor_id`, `action`, `resource_type`, and `resource_id`. The bulk create path inserts the full validated event objects, including optional fields when supplied.

## Endpoints

### Record One Event

```http
POST /events
Content-Type: application/json
```

Returns `201 Created`.

### Record Events in Bulk

```http
POST /events/bulk
Content-Type: application/json
```

The request body must be an array of events. Empty arrays are rejected. The maximum bulk request size is 100 events.

Returns `201 Created`.

### Query Events

```http
GET /events
```

Supported query parameters:

- `actor_id`: comma-separated actor IDs
- `actions`: comma-separated actions
- `resource_type`: comma-separated resource types
- `resource_id`: comma-separated resource IDs
- `from`: date string for timestamp filtering
- `to`: date string for timestamp filtering
- `limit`: page size, defaults to `10`
- `page`: page number, defaults to `1`

The controller currently returns list responses with HTTP status `201`.

### Get One Event by ID

```http
GET /events/:id
```

Returns the event object with `200 OK`, or:

```json
{
  "ok": false,
  "event": null,
  "message": "Event not found"
}
```

with `404 Not Found`.

## Write-Only Decision

Audit logs are meant to be evidence, not mutable application state. This API exposes write endpoints for recording events and read endpoints for retrieving them, but it does not expose update or delete endpoints.

That decision keeps the audit trail append-only:

- existing event rows are not changed through the REST API
- corrections should be recorded as new events
- downstream consumers can treat event IDs and timestamps as stable facts
- accidental or unauthorized mutation is harder because there is no public mutation route for existing records

This does not make the database tamper-proof by itself. Production deployments should still use database permissions, backups, retention rules, and operational controls appropriate for audit data.
